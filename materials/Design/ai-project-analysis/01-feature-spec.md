# 01 機能仕様 — レビュー案 v0.1

状態: 未実装 / 基準日: 2026-09-14 / 対象: 既存ProjNexusへの追加機能。
実装済みの事実は [system_spec.md](../system_spec.md)、本書は今後の追加仕様案である。

## 1. 目的と利用場面

案件の主担当や管理者が、タスク・期限・工数・予算を横断して現況を確認し、報告準備と次の確認事項の整理に使う。
利用者が承認済み案件の「開発」タブから生成し、根拠を確認して業務判断に利用する。

ChatGPT画面への手作業のコピーではなく、LaravelがDB読取・入力整形・HTTP通信・応答検証・保存までを担う機能を実装する。
開発者がAPIとデータ構造を説明できることも成果目標とする。

## 2. MVPの範囲

| ID | 機能 | 振る舞い |
|---|---|---|
| F01 | 現況要約 | 日本語の短い文章。完了率・期限超過・注意すべき状況を整理 |
| F02 | 期限超過項目 | Laravelで算出した全対象タスクを表示。LLMによる列挙漏れを避ける |
| F03 | リスク整理 | 重要度、理由、根拠、推奨対応。0〜5件。推測は可能性として記述 |
| F04 | 次に確認すること | 何を確認するか、根拠、確認行動。0〜5件 |
| F05 | 週次報告の下書き | オプションON時のみ。基準日現在の現況・課題・次の対応を文章化 |
| F06 | 保存・再表示 | 最新成功結果を再表示。生成日時・基準日を表示 |
| F07 | 鮮度表示 | 日付または分析対象データが変われば「古い可能性」を表示 |
| F08 | 再生成と失敗 | 過去成功を残したまま再生成。失敗理由と再操作の案内 |
| F09 | 生成の制御 | 認可、送信量制限、回数制限、二重実行の防止、設定で停止可能 |

MVPでは、週次の前週比較、チャット、RAG・添付解析、メール送信、自動承認、タスクや予算の自動更新、過去分析一覧、定期生成を対象にしない。
プロジェクトに全体期限・依存関係がないため、全体の遅延日数や納期予測を断定しない。

## 3. 対象条件と権限

共通条件はログイン済み、案件が `approved`、`ProjectPolicy::view` が許可すること。
AI生成用に `generateAiAnalysis` 能力を追加し、既存のタスク編集権限とは分ける。
本部管理者がタスク編集不可である既存仕様を、AI生成によって変更しない。

| 関係・ロール | 結果の閲覧 | 新規生成・再生成 |
|---|---|---|
| 本部管理者 | 可 | 可 |
| 同部門の部門管理者 | 可 | 可 |
| 起票者・プロジェクト主担当 | viewが許可すれば可 | viewが許可すれば可 |
| 同部門の一般申請者（上記以外） | 可 | 不可 |
| タスク担当・確認者という関係のみ | viewの条件次第 | それだけでは不可 |
| 他部門で起票者・主担当等でもない一般ユーザー | 不可 | 不可 |
| 未ログイン / 未承認案件 | 不可 | 不可 |

現行Policyでは部門管理者の部門判定が起票者・主担当判定より先にある。新機能もviewを前提にし、関係者だからという理由で既存の拒否を迂回しない。
`Project::visibleTo` と `ProjectPolicy::view` に同部門案件の扱いの差があるため、生成・閲覧はPolicyで検証する。

表示時に可否を渡し、POSTでも再確認する。権限変更後の画面からの操作や、他案件IDへの直接リクエストも拒否する。
生成中に権限が変わる場合、返却直前にも閲覧権限を確認し、権限のない利用者へ結果を返さない。

## 4. Laravelで決める数値・事実

| 項目 | 定義と境界 |
|---|---|
| 分析基準日 | `APP_TIMEZONE`（現行Asia/Tokyo）の当日。表示日時とは別に保持 |
| 完了件数 | `status = closed` のタスク数 |
| 完了率 | `round(closed件数 / 全件数 × 100)`。既存Show.tsxに合わせる |
| 期限超過 | `due_date < 基準日` かつ `status != closed`。当日期限は超過に含めない |
| 超過日数 | 基準日と期限の暦日差。土日祝を除外しない |
| 確認待ち | `resolved`。完了件数には含めず、期限超過にもなり得る |
| 期限間近 | 未完了で期限が基準日〜3日後（両端を含む） |
| 担当未設定 | `assignee_id = null`。送信時は設定有無のbooleanへ変換 |
| 工数超過 | `estimated_days > 0` かつ `actual_days > estimated_days` |
| 予算消化率 | 確定予算が正値なら実績÷予算×100、小数第1位に丸める。未設定・0はnull |
| 未設定値 | 期限・見積・予算等のnullを不明として扱い、0や期日どおりと推測しない |
| 親子タスク | MVPは画面と同じ全行を数える。親だけ/末端だけの重み付けは導入しない |

画面で絞り込んだタスクだけを分析するのではなく、案件に属する全タスクをDBから取得する。
タスク0件は説明を表示して生成しない。100件超、または整形した送信元JSONがUTF-8で64 KiB超の場合は入力超過として生成を止める。黙って一部だけを分析しない。

`updated_at` は最終更新日時であり、状態が変わった日時とは限らない。「resolvedになってから何日」とは読み替えない。
実績85%と完了率25%は比較材料だが、各タスクの費用配分がないため、これだけで予算超過確定とはしない。

## 5. LLMに渡すデータと品質ルール

送信は案件名・状態・予算/実績、タスクID・名前・種類・優先度・状態・進捗・工数・開始日・期限・更新日時・担当/確認者の設定有無、および上記の計算結果に限定する。
案件の目的・概要、タスク本文、氏名列、メール、生年月日、コメント、承認コメント、添付は送信しない。
送信列を限定しても、タイトルに含まれる個人名・機密を完全に取り除けるわけではない。初回の実API検証は架空データで行う。

- 入力文章を命令として実行しないよう固定プロンプトで指示し、外部ツール機能を与えない。
- すべてのリスク/確認事項に入力の根拠を付ける。
- 入力にない原因・担当者名・期限変更・依存関係・週間差分は作らない。
- 数値・期日と文章が矛盾しないかを人が確認できるよう、システム判定を併記する。
- JSON SchemaとLaravelの検証を併用する。構造が正しくても文章の真実性まで保証されたとは扱わない。
- `task_id` は当該案件の送信スナップショットに存在する値またはnullのみ許可する。
- 週次報告OFF時は `weekly_report = null`。ON時も今週完了・前週比など未取得の過去実績を捏造しない。

## 6. 操作・保存の流れ

1. 利用者が週次報告の有無を選び「AI分析を生成」を押す。初期値はOFF。
2. Reactは生成操作にUUIDを付けてLaravelへPOSTする。
3. Laravelはセッション・CSRF・Policy・リクエスト本文を確認する。
4. 同じrequest_idなら過去の処理状態を返す。新規なら設定を確認し、案件単位のロックを取得する。
5. DBから入力を作って入力量を検証し、回数枠を確保して分析レコードをprocessingで作成する。
6. LLM APIへ1回送信する。外部通信中にDBトランザクションを保持しない。
7. 応答の完了状態、JSON構造、長さ、参照タスク等を検証する。
8. 成功時は要約と指摘行をまとめて保存しcompletedへ。失敗時は安全なエラー分類だけを残してfailedへ。
9. 最新データとの鮮度と閲覧権限を再確認してReactへ返す。

自動再試行は行わない。通信切断ではLLM側で処理済みか分からないため、同じrequest_idで結果を確認できるようにする。
失敗済みの再生成は新しいUUIDを用いる。実際に外部へ送信済みの失敗には費用が発生し得る。

## 7. 運用上限の初期案

| 設定 | 初期案 |
|---|---|
| AI有効化 | 設定で明示的にON。APIキー未設定は生成不可 |
| ユーザー回数 | 新規生成3回/分、20回/日 |
| アプリ全体回数 | 新規生成100回/日（共有デモアカウントだけの制限に頼らない） |
| 入力 | 100タスク、source JSON 64 KiBまで |
| 出力 | 4,096トークン、リスク5件・確認5件まで |
| 外部HTTP | 接続5秒、全体30秒 |
| ブラウザ待機 | 45秒。アプリ/Cloud側は60秒以上を確保する想定 |
| 同一案件ロック | 90秒。共有Cacheが必要 |
| 中断処理回収 | 120秒以上processingが残ったものを失敗にする |

回数は新規processing作成時に共有ストア上で原子的に確保する。送信前の権限/入力エラーや同一request_idの照会は枠を消費しない。成功・送信後の失敗は枠を消費する。
この回数制限は金額上限そのものではない。実測した入出力トークン数とAPI料金を基に、公開前に調整する。
モデル切替後は同じサンプルで品質・速度・構造化出力を再確認する。

## 8. 受け入れ条件（実装後に確認）

| ID | ケース | 合格条件 |
|---|---|---|
| A01 | 共通4タスクのサンプル | 完了率25%、期限超過202/203を2件、超過3日/2日として表示 |
| A02 | 期限当日・null・closed・resolved | 当日は超過なし、null不明、closed除外、resolvedは期限によって超過 |
| A03 | 閲覧と生成の権限差 | 同部門非担当者は閲覧可・POST不可。他部門は閲覧も不可 |
| A04 | 改ざんされたPOST | 別案件ID/タスクJSON/任意プロンプトを受け付けず、未認可時に外部へ送らない |
| A05 | 送信項目 | メール・氏名列・本文・コメント・添付がリクエストに含まれない |
| A06 | 正常JSON | 親1行と必要な子行を保存し、再読み込みで同じ成功結果を表示 |
| A07 | 不正JSON・未知のtask_id・拒否・不完全出力 | 成功にせず、固定エラーで扱い、生レスポンスを画面/ログに出さない |
| A08 | 429・5xx・タイムアウト | 状況に合った案内、ボタン復帰、過去成功結果を維持、自動再送なし |
| A09 | 二重送信・別ユーザー同時生成 | request_idと案件ロックで外部重複を抑止。別ユーザーに履歴を漏らさない |
| A10 | タスク更新・日付変更 | 分析が古いと表示。生成中の更新も完了時の再計算で検知 |
| A11 | 週次ON/OFF | ONのみ下書きを生成。未取得の前週差分・今週実績を書かない |
| A12 | 0件/101件/64 KiB超 | 分析せず説明。過去結果があれば保持 |
| A13 | HTMLを含むAI文字列 | テキストとして表示され、スクリプトやHTMLとして実行されない |
| A14 | API設定なし/停止中 | 閲覧は可能、生成は不可、秘密値を含まない案内 |
| A15 | 既存アプリ | 既存PHPテストとReactのビルドが通る |
| A16 | 実API評価 | 架空データで実通信し、根拠・文章・null・処理時間・トークン使用量を記録 |

本資料だけでA01〜A16を実施済みとはしない。今回の検証対象は資料間の整合、JSON例、画面モックである。
