## この案の要点

- 承認済み案件の「開発」タブ、既存進捗サマリーとタスク表の間にAIカードを置く。
- **期限超過・完了率はLaravelで計算**し、LLMは要約・リスク・確認事項・報告下書きを作る。
- 既存画面の完了率は `closed件数 / 全タスク数`。個々の進捗率の平均とは異なる。
- 週次報告は「基準日現在の状況から作る下書き」。前週との差分や今週の完了実績はMVPの対象外。
- 分析1回を親テーブル、複数の指摘を子テーブルへ保存する。
- 元データはLaravelがDBから読み、専用の送信項目だけを組み立てる。
- LLMは業務データの更新や外部ツールの実行を行わない。
- モデルは設定で差し替え可能。JSON例の初期候補は `gpt-4.1-mini`。実通信で品質・時間・利用可否を検証して採用を確定する。

## 実装へ渡す判断と残る検証

| 判断 | この設計案での扱い |
|---|---|
| 誰が費用の発生する生成をするか | 本部管理者、同部門の部門管理者、起票者、主担当。全員に案件view権限を要求 |
| 結果の閲覧者 | 承認済み案件のview権限を持つユーザー。生成権限より広い |
| 外部に送る文章 | 案件名・タスク名のみ。目的・概要・詳細本文・コメント・氏名列等は除外 |
| 自由入力のタイトル | 個人名・機密が含まれる可能性は残る。完全匿名化とは説明しない。実通信デモは架空データで行う |
| 生成方式 | 同期HTTP。自動再試行なし。二重送信はrequest_idと案件単位のロックで制御 |
| 履歴の見せ方 | MVP画面は最新の成功結果。失敗記録もDBに残す。履歴一覧画面は将来 |
| 品質と費用 | 実装後に同一サンプルで実APIを試験し、モデル・タイムアウト・上限を調整 |
| 公開・デプロイ | 実装と検証後。Cloud設定確認は後続作業 |

## 理解して説明できるようにするポイント

1. **Web/API**: ページ描画はInertiaを継続し、生成操作だけ同一オリジンのJSONエンドポイントにする理由を説明する。
2. **データ構造**: DBの行全体を送らず、用途に合わせた入力JSONを組み立てる。JSON Schemaは出力の構造契約であり、文章の真偽の保証ではない。
3. **DB設計**: 1回の分析に複数の指摘があるため1対多に分ける。入力スナップショットを保存する理由と、現在データとの違いを説明する。
4. **LLM API**: 認証ヘッダー、HTTPリクエスト、応答の解析、検証、失敗処理をアプリケーションとして実装する。
5. **評価**: 自動テストで確認できる権限・計算・保存と、人が確認する要約の妥当性を区別する。
